# new-api 模型网关 + 家宽服务器：我的自托管 AI 基础设施

## 这套基础设施解决什么问题

玩 AI 应用跑不掉三件事：**模型从哪来、服务跑在哪、外网怎么访问**。我的答案是一套完全自托管的基础设施：

- **模型层**：new-api 网关统一接入 27 个国产模型、5 个上游渠道
- **算力层**：家宽服务器跑服务，数据留在自己手里
- **入口层**：阿里云轻量服务器做反向代理，域名 + HTTPS + frp 隧道

## 模型网关：为什么中间一定要加一层

让每个应用各自配模型 API，很快就乱：key 散落各处、额度没人管、上游一挂应用跟着挂。加一层 new-api 网关之后：

```
WeKnora / 其他应用 ──┐
脚本 / 实验程序   ──┼──► new-api 网关 ──► 渠道1（主力模型）
                  │         │         渠道2（备胎）
                  └────────► 渠道3（便宜模型，跑批量任务）
```

几个实际收益：

1. **一处配 key**：应用只认网关地址和网关发的令牌，上游 key 永不下发给应用
2. **故障切换**：主力渠道超时自动切备胎，半夜上游抽风也能睡安稳觉
3. **额度与审计**：每个令牌的调用量、花费清晰可查，给不同应用发不同令牌
4. **激活码体系**：想给别人临时用，发个带额度的码就行，不用共享主 key

## 家宽服务器：数据落地的取舍

家宽跑服务最大的顾虑是稳定性和安全，我的取舍是：

- **家宽机器只跑数据与计算**：知识库、向量库、网关全在这，断网也不丢数据
- **云上机器只做入口**：反代 + 证书 + frp server，被打了也只损失入口
- **敏感接口不暴露**：管理后台只走内网或 VPN，公网只开放必要的 webhook

### frp 隧道要点

```ini
# frpc.toml（家宽侧，节选）
[[proxies]]
name = "web-ui"
type = "tcp"
localPort = 8080
remotePort = 18080

[[proxies]]
name = "api-hook"
type = "tcp"
localPort = 9090
remotePort = 19090
```

三个踩坑点：

1. **家宽重拨 IP 会变**：frpc 心跳 + 自动重连要打开，另外建议给家宽机器配个 watchdog 脚本，断了自动拉起
2. **上游超时要对齐**：Nginx 的 `proxy_read_timeout` 要大于下游最长响应时间，长回答（流式输出）尤其容易踩
3. **WebSocket 记得升级头**：反代到有 WS 的服务，`Upgrade` / `Connection` 两个头不配，页面能开但功能全哑

### HTTPS 与证书

域名解析到云上机器，acme 自动签发续期，Nginx 终结 TLS 后转发 frp 端口。整条链路对用户就是普通 HTTPS，感受不到后面是台家宽机器。

## 性能与成本

- 8G 内存的家宽机器，知识库全家桶 + 网关 + frp 常驻占用约 60%，限制各容器内存后稳定运行
- 全套固定成本 = 一台入门云主机 + 家里电费，模型费用按量走 API，比任何订阅制都便宜
- 实测微信问答链路首字响应 0.7 秒，检索 + 推理全链路在家宽机器上完成

## 这套东西和我的服务

这套基础设施我已经跑了大半年，期间把配置全部 IaC 化、流程写成了 SOP。如果你也想把知识库跑在自己的机器上，可以看看我的 [WeKnora 私有部署服务](/services)，基础架构就是本文这套，[这篇实战记录](/post/weknora-deploy) 有更完整的部署过程。

## 写在最后

自托管不是省事的选择，但它是**把控制权拿回自己手里**的选择。模型会换、产品会停，只有数据和调用链路在自己手里，应用才真正属于你。
